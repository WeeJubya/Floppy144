# B2-02: Independently implemented Windows runtime, behavioural specification

**Status:** implementation-neutral specification, 21 October 2026. **No production code change.** Normative terms: **MUST** denotes compatibility/acceptance requirement; **SHOULD** denotes a recommended behaviour which requires a documented justification to omit; **OPEN** means not yet confirmed by recorded baseline evidence.

## 1. Scope, precedence and source discipline

Create an independently authored C99 Windows x64 runtime that exposes the **existing** public game-facing `F144PlatformApi` and presents the game's own software-drawn pixels. The replacement MUST be part of the single `Floppy144.exe` executable; MUST use documented Win32 and GDI facilities, the Windows SDK and existing MSVC/VS2022 build; MUST NOT require an external graphics engine, SDL/OpenGL/DirectX runtime, River2D DLL, network service or stored audio. Game-specific drawing and gameplay remain in `Floppy144Core`. Native window/presentation code must not enter game rendering modules.

**Source-of-truth order:** (1) public `include/f144_platform.h` and associated project-owned interfaces; (2) B2-01 `01_baseline.md` observable acceptance facts; (3) existing project-owned regression expectations; (4) published Beta.1 captures and human-reviewed reference recordings **once produced**; (5) Microsoft Win32 API documentation. Historical `01_provenance_inventory.md` is for the rights/provenance reviewer **only**, not the implementer. Conflicting or missing observations must be recorded, not reverse-engineered from the inherited implementation. Full Beta.1 visual/hash sign-off is currently OPEN.

The frozen *published* Beta.1 reference is `GreyDoorRepublik/Floppy144-beta` commit `0981e4ab3694a1cdb5b6338c199e0262a6ed14bf`; the implementation **development** branch is `WeeJubya/Floppy144:development/Beta-2-runtime`, initially based on Stage-4 commit `46c2a81e097abf69734a4b2f0b7bc91f9142c256`. These trees are not identical. Refer to the published EXE for Beta.1 observations; preserve later approved game behaviour on the active development branch.

## 2. Software framebuffer, format, ownership

- Logical image dimensions MUST remain **640 columns × 360 rows**, independent of window size. The required pixel array is **230,400 unsigned 32-bit elements = 921,600 bytes**, with a logical row length of **640 pixels = 2,560 bytes**. An implementation may choose a larger internal allocation for guards or scratch space, but the **exposed** surface MUST have exactly the public dimensions.
- The public `Floppy144Surface` holds a writable `uint32_t *pixels` with `width=640` and `height=360` whenever drawing is possible. Pixel index `(x,y)` denotes the pixel at the corresponding left-to-right, **top-to-bottom** position, with origin at the upper left. Valid coordinates are `0..639`, `0..359`.
- A pixel's low 24 bits carry colour in the **0x00RRGGBB** convention. Red `0x00FF0000`, green `0x0000FF00`, blue `0x000000FF`, white `0x00FFFFFF`, black `0x00000000`. High eight bits have **no semantic alpha**; the presenter must ignore/mask them consistently and may standardise them to zero at display transfer. Tests include high-byte nonzero values to prove it does not alter RGB.
- Win32 x64 uses little-endian byte ordering. When transferred to a 32-bit BI_RGB GDI bitmap, the byte sequence for `0x00RRGGBB` is blue, green, red, unused. This does **not** change the contract seen by drawing code. No per-pixel red/blue exchange, premultiplication, automatic gamma correction, interpolation or alpha blending is permitted at the presentation boundary.
- Any DIB interpretation must use a **top-down** 32-bit image and an uncompressed RGB-compatible format. Microsoft's `BITMAPINFOHEADER` specifies negative `biHeight` for top-down RGB DIBs. Only positive, checked dimensions may reach native calls. At 640 × 360 all scanlines are DWORD-aligned.
- Runtime owns pixel storage. Game drawing borrows the pointer, never frees/reallocates it, and never holds it after shutdown. `framebuffer` returns a valid surface only after successful initialisation. Window resize MUST NOT invalidate the borrowed pixel pointer, because the **logical** image is fixed size. Storage may change only at a documented quiescent reinitialisation; the caller must not be concurrently drawing/presenting when a change occurs.
- All allocation, dimension arithmetic and potential offset/stride calculations MUST be checked for unsigned overflow *before* allocation and multiplication. Reject NULL, zero/negative client dimensions when painting, impossible bitmap dimensions and overflow. Clear newly committed memory to deterministic black before first game draw; do not expose uninitialised pixels. Free exactly once on normal, partial-init and repeated shutdown paths. Failure to allocate the required surface MUST fail startup cleanly, never provide a non-NULL invalid surface.
- The UI/rendering thread and frame-presentation protocol MUST prevent a screen copy from seeing partially written frames. Single-threaded draw/commit/paint scheduling or independently allocated stable published frames are acceptable. The implementation can use any independently devised allocation/queuing method satisfying these requirements.

**Reference:** [Microsoft DIB formats](https://learn.microsoft.com/en-us/windows/win32/gdi/device-independent-bitmaps), [StretchDIBits](https://learn.microsoft.com/en-us/windows/win32/api/wingdi/nf-wingdi-stretchdibits).

## 3. Client-area scaling and image placement

- Native resize modifies **only** the window client rectangle and presentation destination. Use `GetClientRect` (not outer window bounds) for drawing-area dimensions; compute all coordinates in client pixels, with a consistent DPI awareness policy.
- Retain **16:9**, no cropping, no stretch-to-fill and no smooth resampling. The entire logical frame MUST fit in the positive-sized client rectangle; unused areas are opaque black side or top/bottom bands. The 640 × 360 frame remains centred.
- Define the target destination **geometrically**: choose the largest axis-aligned, centred 16:9 rectangle that fits. For deterministic integer test results, use **floor** when converting the unconstrained dimension from the constraining dimension; on positive tiny windows where floor gives zero, clamp both sides to at least one client pixel without exceeding the available client size. Integer division calculations must use widened intermediates. Remaining odd pixels are assigned with floor-to-left/top and residual-to-right/bottom. The displayed aspect ratio may deviate by under one device pixel due to rounding; do not use integer-only multiples that leave avoidable unused space at intermediate sizes.
- Use a GDI copy/stretch transfer that preserves nearest/selective pixel edges (e.g. documented `COLORONCOLOR` behaviour) rather than smooth interpolation. A neighbouring red and blue pair must never generate blended intermediate colours. Support clients smaller than logical resolution, native size, multiples and non-integer enlargements.
- Required destination test oracles (W×H means **client area**, rectangle is x,y,width,height):
  
  | Client W×H | Game rectangle x,y,w,h | Bands |
  |---|---|---|
  | 640×360 | 0,0,640,360 | none |
  | 1280×720 | 0,0,1280,720 | none |
  | 800×600 | 0,75,800,450 | top/bottom 75 |
  | 1000×700 | 0,69,1000,562 | top/bottom 69 |
  | 1200×500 | 156,0,888,500 | left/right 156 |
  | 1024×768 | 0,96,1024,576 | top/bottom 96 |
  | 700×1000 | 0,303,700,393 | top 303, bottom 304 |
  | 320×180 | 0,0,320,180 | none |
  | 1×1 | 0,0,1,1 | degenerate pixel-only case |
  | 0×360 or 640×0 | no transfer | no divide by zero |

- Follow Windows DPI notifications and re-read the current client rectangle rather than assuming initial monitor DPI; no change to logical 640×360. Exact DPI-awareness manifest and minimum supported Windows build remain **OPEN**, subject to Beta.1 compatibility evidence.

**References:** [GetClientRect](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getclientrect), [SetStretchBltMode](https://learn.microsoft.com/en-us/windows/win32/api/wingdi/nf-wingdi-setstretchbltmode), [DPI guidance](https://learn.microsoft.com/en-gb/windows/win32/hidpi/high-dpi-desktop-application-development-on-windows).

## 4. Window lifecycle and painting

- The launcher must register a suitable native window class, create one top-level resizable window with the established game title/icon, initialise framebuffer and platform services, enter a normal Win32 message pump, and release all resources on exit. Use the published game for any unverified initial outer position/size or style rather than guessing. Achieve any requested initial **client** area by accounting for window chrome and DPI.
- Correctly process at minimum creation failure, show/activate, `WM_SIZE`, `WM_PAINT`, `WM_ERASEBKGND`, `WM_ACTIVATEAPP`, keyboard/text messages, `WM_CLOSE`, `WM_DESTROY` and `WM_NCDESTROY` as applicable; unhandled messages go to Windows default handling. A paint must validate the update region through normal `BeginPaint`/`EndPaint` handling, including where no frame is yet available.
- On expose or resize, repaint from the **last fully committed frame**; do not force the game to re-run world simulation solely to answer an OS repaint. Repeated `WM_PAINT` with unchanged frame and client dimensions must produce identical client pixels. The title bar is outside this paint contract.
- **No intermediate black flash:** do not erase or fill the live destination game rectangle immediately before painting the image. The backbuffer content should be painted/committed coherently; only paint necessary unused letterbox/pillarbox regions black as part of the same repaint sequence. Manage `WM_ERASEBKGND` consistently with full client-area ownership, and never assert background handling succeeded if the region will not actually be painted. A transient black frame is not an acceptable presentation artefact.
- On `WM_SIZE` with zero client width or height (minimised/hidden), **suppress bitmap transfer**, retain the valid 640×360 source and avoid divide-by-zero/GDI calls with invalid destination dimensions; repaint when a positive-size client returns. On resize or DPI change use the updated client rectangle. Do not assume client width equals window width.
- Window close must first translate and deliver one orderly shutdown request through the existing lifecycle route; allow the game to perform its normal save policy, then destroy the window once and report completed shutdown. `WM_DESTROY` should end the message loop; `WM_NCDESTROY` must not access freed state. Quit and destruction are idempotent from the game's perspective. Dispose window-only, GDI, timer, audio and single-instance resources in a defined, safe order; Windows handles must not leak after partial initialisation.
- Handle each of the three `GetMessage` results correctly: positive means dispatch, zero means quit, **-1 means error**. Window registration, creation, allocation, painting, timer setup and API failure paths must be checked and return a meaningful status instead of silently continuing with an invalid handle.

**References:** [WM_PAINT](https://learn.microsoft.com/en-us/windows/win32/gdi/wm-paint), [BeginPaint](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-beginpaint), [Window background](https://learn.microsoft.com/en-us/windows/win32/gdi/window-background), [DestroyWindow](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-destroywindow), [GetMessage](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getmessage).

## 5. Logical input, text and focus

- Physical key information MUST be translated at the Windows boundary to `F144ActionEvent`, with `action`, `type` (DOWN/UP) and a matching opaque `physical_token`. The game never receives HWND, VK codes or native message structures as gameplay policy inputs.
- Required project regression mapping: ↑/↓/←/→ = movement; W/S = menu/list navigation up/down; A = access; I = inspect; Return = confirm; Backspace = back; Page Up/Down = page actions; N = notebook; Escape = session control. Unmapped Q, digit 0 and Space remain eligible for text/pager operations, not gameplay actions. Contextual interpretation of actions is owned by game code, not the runtime. Opposite cardinal holds cancel; diagonals are derived by holding one horizontal and one vertical direction, never emitted as separate platform actions.
- Key down/up token pairing MUST be stable across repeats, and a released physical key must never remain logically held. Repeated native keydown messages must not multiply the movement-held state. Preserve text entry repeat according to existing terminal behaviour; do not conflate translated key events with `WM_CHAR` text delivery. On focus loss and shutdown, cancel/release held keys so movement cannot stick on return. Define an explicit key-state test for focus interruption.
- Text events use `F144TextInputEvent.codepoint` as 32-bit values. `WM_CHAR` supplies ordinary translated text, not a substitute for physical actions. The current terminal/cabinet need ASCII and control-input behaviour, including letters, digits, Backspace and Return where handled by the existing game. Do not promise full Unicode/IME support without tests; any Unicode expansion is a separate approved feature. Preserve any native repeat/keyboard layout behaviour verified in Beta.1.
- `WM_ACTIVATEAPP` active/inactive must map to the game lifecycle state. An inactive window must not trigger gameplay actions from stale state.

**References:** [WM_CHAR](https://learn.microsoft.com/en-us/windows/win32/inputdev/wm-char), [Keyboard messages](https://learn.microsoft.com/en-us/windows/win32/inputdev/about-keyboard-input), [WM_KILLFOCUS](https://learn.microsoft.com/en-us/windows/win32/inputdev/wm-killfocus).

## 6. Timing, lifecycle, storage, single-instance, audio

- The Windows backend supplies a **monotonic `uint64_t` millisecond clock** and wake opportunities, not the game's timing rules. The project-owned `Floppy144TimingAdvance` retains animation 16ms, terminal restore 50ms, cursor toggle 500ms, autosave and safe missed-tick semantics. No wall-clock-dependent gameplay cadence; clock rollback tests must not underflow. Actual wake interval policy remains defined by the existing game/timing tests.
- Preserve lifecycle events `START, ACTIVE, INACTIVE, SUSPEND, RESUME, SHUTDOWN_REQUESTED, SHUTDOWN`. From existing tests, `WM_ACTIVATEAPP(TRUE/FALSE)` maps ACTIVE/INACTIVE; `WM_CLOSE` maps SHUTDOWN_REQUESTED; `WM_DESTROY` maps SHUTDOWN. No unsolicited autosave on ordinary Win32 focus loss; `request_autosave` only when the established game/platform policy requests it.
- Reuse existing project-owned storage path and persistence services. The platform's persistence file categories are manual save, autosave, profile, settings; legacy lookup candidates remain supported. **Do not change on-disk schemas, migration, atomic write guarantees, directory locations or profile naming.** Failure to resolve a writable path must not corrupt existing files.
- Single-instance acquisition remains launcher-owned, before normal startup, using the existing profile-scoped mutex/service contract. An already-running instance must not start a second active game or overwrite the first instance's state; release ownership on every exit/error path.
- WinMM MIDI and waveOut playback stays **procedural**. Preserve existing semantic music/SFX cue IDs, volume range 0..10, update with monotonic time/recovery percent, tempo state, mute and shutdown behaviour. The replacement display backend may **reuse project-owned audio services**, but must not import an engine, store PCM/music as assets or reinterpret audio from graphics code. Audio device failure should not crash the display loop.
- Preserve existing local calendar, startup developer flags, recovery seed/fixed-date options without persisting transient flags.

## 7. Errors and resource ownership

The clean backend must treat the following as testable outcomes, not undefined behaviour: window registration failure; failed window creation; invalid/missing device context; memory allocation denied; overflow or dimensions beyond native signed limits; zero-sized client; repeated resize; monitor/DPI change; loss/recovery of focus; lost audio device; save path failure; timer creation failure; double close; failure to paint; error return from message pump. In any state, the game surface is either valid and fully initialised or unavailable, never half-valid. Graceful failure may terminate startup with an error status; once running, recoverable painting/timer failures must not corrupt the game. Count surviving handles/allocations before and after shutdown.

## 8. Verification/definition of compatibility

- Maintain exact `F144PlatformApi` binary/source expectations defined in `02_api_contract.md`, including field order and callback semantics. No new members, enum re-numbering or Windows types in game-facing headers. If the main coordinator currently depends on an inherited private runtime type, remove only the **adapter coupling** in a separately reviewed integration change; do not carry the private type into the replacement.
- The known test oracles and new acceptance IDs are in `02_acceptance_matrix.md`. Headless and Win32 integration tests must pass in Debug/ASan where applicable and in strict WarningLevel4/WarningsAsErrors clean Release. The executable MUST be at most **1,474,560 bytes** (Beta.1 release metadata: 822,272).
- Binary/pixel reference acceptance is **blocked by missing independently verified published EXE hash and approved framebuffer/screenshots**; this is a baseline-evidence dependency, not permission to inspect derived source. The project owner must confirm image/audio/manual differences.
- Do not claim a visual, Windows, audio or regression pass until actually run. All clean implementation commits and a source expression/lineage review are deferred to B2-03.
