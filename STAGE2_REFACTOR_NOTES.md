# Floppy//144 Stage 2 Refactor Notes

## Architectural boundary

Stage 2 separates **game definition** from **game capability**.

The approved `data/floppy144_game_data.json` defines what exists and what should
happen. The C runtime defines a compact vocabulary for evaluating conditions,
executing effects, resolving evidence, interpreting interactions, drawing data
recipes and rendering the Site.

The build-time compiler translates stable JSON strings into generated tables,
so the shipping executable does not carry a general JSON parser.

## Generic progression

`floppy144_game_data.c` and the small trigger/interaction wrappers interpret
stable data records. Persistent facts remain in `Floppy144RunState` bitsets and
enums. Derived facts, including unlocked connections, enabled collections and
revealed physical items, are reconstructed from completed persistent actions
and their generated effects.

This avoids duplicating the same state in two places and preserves a compact
save structure.

### Order-independent evidence

Evidence synthesis requirements are resolved after interactions. When the JSON
marks a synthesis as order-independent, one half of a pair can be inspected
before the other. The individual interaction remains remembered; evidence is
established only when all synthesis requirements are satisfied.

## Documents

`floppy144_documents.generated.inc` contains all readable Stage 2 document
metadata and full body text generated from the canonical JSON. The catalogue
viewer renders the generated body rather than maintaining separate prose in C.

## Physical interactions

Migrated office objects carry a canonical physical item ID such as `P-012`.
The office dispatcher resolves that ID to the generated interaction ledger and
runs the generic prerequisite/effect engine. Bespoke P-012/P-033/P-014 effect
arrays have been removed.

## Isometric 2.5D

`floppy144_site_isometric.c` is a presentation-only projection over the same
100 x 100 Site geometry used by collision and room classification. It does not
create a second map.

The persistent projection enum remains authoritative. FM-23 sets it using the
normal JSON `SET_PROJECTION` effect; `Floppy144RunStateIsIsometric()` exposes a
boolean query for presentation code.

## Drawing recipes

`floppy144_drawing_runtime.c` interprets generated JSON drawing primitives.
Furniture and physical-item artwork can therefore share a compact primitive
vocabulary instead of requiring a `DrawXxx()` function per object.

## Generated files

The following are generated by `tools/game_data_compiler.c` and should not be
hand-edited:

- `game/src/floppy144_game_data.generated.inc`
- `game/src/floppy144_documents.generated.inc`
- `game/src/floppy144_collections.generated.def`
- `game/src/floppy144_triggers.generated.def`
- `game/src/floppy144_interactions.generated.def`
- `game/src/floppy144_evidence.generated.def`
- `game/src/floppy144_physical_items.generated.inc`
- `game/src/floppy144_ambient.generated.inc`
- `game/src/floppy144_runtime_ledger.generated.inc`
- `game/src/site_layout.generated.jsonc`

The build also synchronises the generated collection/trigger/interaction/
evidence `.def` files used by their public enum headers.

- 50 triggers;
- 40 interactions;
- 23 evidence definitions;
- 11 rooms;
- 16 connections;
- 151 furniture records;
- 91 fixtures;
- 161 physical items;
- 44 colours;
- 24 drawings;
- 16 ambient/seasonal interactions;
- generic early-route trigger execution;
- data-derived connection unlock and physical reveal state;
- FM-23 projection switching;
- reversed/order-independent evidence synthesis;
- all 40 physical-source mappings;
- Hallowe'en noticeboard selection;
- drawing recipe interpretation;
- Act II core-complete inference from the generated selected-branch graph.

The Windows `run.ps1` build repeats these tests before building the GUI game.
